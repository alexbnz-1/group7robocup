1. PURPOSE OF THIS FILE
===============================================================================

This file is the self-contained technical handover for the repository. It
records what exists, how the pieces connect, what has been verified, what is
currently only present in the working tree, and what remains to be integrated
or tested. A new team member should read this file before changing firmware,
wiring, the Bluetooth protocol, or the desktop tools.

The project currently consists of four main areas:

1. Teensy 4.0 firmware managed by PlatformIO.
2. A live Bluetooth/serial robot-debugging GUI.
3. Recording, visualisation, and command-line analysis tools for saved runs.
4. A collection of supplied hardware example sketches used as references.

The newest work makes the debug GUI data-driven. GUI parameter and command
controls are described in one JSON file. The PlatformIO build validates and
embeds that JSON, while a firmware library handles the complete serial workflow.

2. CURRENT HARDWARE COMMUNICATION LAYOUT
===============================================================================

Controller:

- Teensy 4.0.
- Firmware framework: Arduino through PlatformIO.
- Firmware environment name: teensy40.

Bluetooth debug connection:

- Hardware: supplied, pre-matched CH9143 Bluetooth serial board pair.
- One board plugs into the robot carrier board.
- The other board connects to the computer through USB-C.
- The pair behaves as a transparent serial cable. The desktop software sees a
  conventional Windows COM port and does not implement a separate radio layer.
- Robot-side connector: SERIAL1.
- Teensy UART: Serial1.
- Teensy Serial1 pins: RX1 pin 0 and TX1 pin 1.
- Baud rate: 115200.
- Framing: 8 data bits, no parity, 1 stop bit.
- Application framing: one JSON object followed by a newline.
- During verified testing, Windows identified the receiver as
  "USB-BLE-SERIAL CH9143" on COM10.
- During the same testing, COM7 was the Teensy's direct USB programming port.
- COM numbers are assigned by Windows and may change. Select the device by its
  description instead of relying permanently on COM10.

Herkulex smart-servo connection:

- Bluetooth now occupies SERIAL1.
- The Herkulex bus is therefore configured to use Teensy Serial2.
- The Herkulex cable must be plugged into the carrier board's SERIAL2 connector.
- Servo UART baud rate: 115200.
- Sorting-gate default ID: 1.
- Kicker-cam default ID: 2.
- Accepted position-command range: approximately -160 to +160 degrees.
- Movement time accepted by the debug command: 50 to 2850 ms.
- Startup, STOP, and leaving Debug Mode disable broadcast servo torque.

Important configuration inconsistency to clean up:

- PlatformIO/include/config.h correctly assigns HerkulexConfig::PORT to
  Serial2 and BluetoothConfig::PORT to Serial1.
- The older Pins::SMART_SERVO_RX and Pins::SMART_SERVO_TX constants and nearby
  comments still say pins 0 and 1. Those constants are stale and conflict with
  the current Serial2 assignment. The active workflow uses the HardwareSerial
  object, so the working code is not using those stale constants, but the names
  and comments should be corrected before other firmware starts depending on
  them.

Other configured hardware assignments:

- Drive left PPM: pin 2.
- Drive right PPM: pin 3.
- Reel left PPM: pin 4.
- Reel right PPM: pin 5.
- Front ultrasonic trigger: pin 9.
- Front ultrasonic echo: pin 10.
- Inductive proximity input: pin 11.
- Left analogue IR: A0.
- Right analogue IR: A1.
- TOF sensor bus: Wire / I2C bus 0.
- Colour sensor bus: Wire1 / I2C bus 1.
- SX1509 expander address: 0x3F.
- Runtime-configured point TOF addresses use 0x40 through 0x47.

Several values in config.h are explicitly placeholders. Sorting-gate angles,
kicker angles, sensor counts, XSHUT expander pins, and the analogue IR presence
threshold must be tuned or confirmed on the completed robot.

4. CURRENT MAIN PROGRAM
===============================================================================

File:

    PlatformIO/src/main.cpp

The file has deliberately been reduced to construction and two calls. It:

- Creates one BluetoothDebugWorkflow object.
- Passes it the configured Bluetooth and Herkulex UARTs.
- Calls debugGui.begin() once from setup().
- Calls debugGui.update() repeatedly from loop().

There is no protocol parsing, JSON construction, command dispatch, telemetry
formatting, or servo-control logic in main.cpp. This is intentional. Future
normal robot operations can be added around debugGui.update() without moving
the debugging implementation back into main.cpp.

5. JSON-DRIVEN GUI CONFIGURATION
===============================================================================

Human-edited source file:

    PlatformIO/debug_config.json

Generated build file:

    PlatformIO/include/debug_config.generated.h

Generator:

    PlatformIO/scripts/embed_debug_config.py

Detailed editing guide:

    PlatformIO/DEBUG_GUI_CONFIG.md

Build process:

1. PlatformIO runs embed_debug_config.py before compiling firmware.
2. The script reads debug_config.json using Python's strict JSON parser.
3. Invalid JSON stops the build and reports the editing error early.
4. Valid JSON is compacted.
5. The compact JSON is written into debug_config.generated.h as a C++ string.
6. The BluetoothDebugWorkflow library parses the embedded string during Teensy
   startup.
7. When the desktop GUI connects, the library advertises every configured
   parameter and command.

Do not edit debug_config.generated.h manually. Any manual edit will be replaced
on the next PlatformIO build.

Current JSON parameters:

- debug.telemetry_interval_ms
  - Label: Telemetry interval.
  - Type: integer.
  - Unit: milliseconds.
  - Default: 200 ms, giving 5 telemetry updates per second.
  - Minimum: 50 ms.
  - Maximum: 2000 ms.
  - Step: 50 ms.
  - This parameter is connected to live behavior; changing it changes the
    actual firmware telemetry period.

Current JSON commands:

- ping
  - Action: ping.
  - No arguments.
  - Returns "Pong from Teensy" as a log and sends current state.

- stop
  - Action: stop.
  - No arguments.
  - Broadcasts torque-off to the Herkulex bus.
  - Sets stopped state true.
  - Sends state and a warning log.

- run
  - Label: Run Robot.
  - Action: run.
  - Requires Debug Mode.
  - Clears stopped mode without moving or energising a servo by itself.
  - A relative movement command remains necessary before torque is enabled.

- set_herkulex_angle
  - Label: Set Herkulex angle.
  - Action: herkulex_angle.
  - Requires Debug Mode.
  - Arguments:
      id: integer from 1 through 253, default 1.
      angle_deg: numeric from -160 through +160, default 0.
      move_time_ms: integer from 50 through 2850, default 500.
  - Clears the selected servo's errors, enables its torque, sends the movement,
    updates commanded-position telemetry, and reports running state.

- read_herkulex_angle
  - Label: Read Herkulex angle.
  - Action: herkulex_read_angle.
  - Argument: servo ID from 1 through 253, default 1.
  - Requests position feedback from the selected servo.
  - Publishes a valid result as servo.measured_angle_deg telemetry.
  - Reports an error if no valid response packet is received.
  - The first successful manual read enables automatic reads for that servo ID
    every 200 ms until the Teensy resets.

- zero_herkulex_here
  - Label: Zero Herkulex here.
  - Action: herkulex_zero_here.
  - Argument: servo ID from 1 through 253, default 1.
  - Reads the current physical position without moving the servo.
  - Stores that position as the temporary software-zero offset for that ID.
  - All later movement angles for that ID are interpreted relative to this zero.
  - The offset is held in RAM and is cleared by reset or power loss.
  - Movement is rejected until the selected servo has been zeroed.

What is automatic when editing JSON:

- Adding a parameter object creates a GUI parameter control.
- Removing a parameter object removes that control.
- Numeric parameter changes are validated, clamped to JSON min/max values,
  held in Teensy RAM, and confirmed to the GUI.
- Adding a command object creates a GUI command control.
- Removing a command object removes that control.
- Command arguments generate the appropriate integer/float/boolean/string/enum
  controls supported by the desktop GUI.
- Setting debug_mode_required protects a command until Debug Mode is enabled.
- Selecting an already implemented action connects the GUI command to that
  firmware behavior.

What is not possible from JSON alone:

- JSON can describe a control and select an existing action, but it cannot
  invent new electrical or mechanical behavior.
- A completely new action name requires one matching C++ implementation in
  BluetoothDebugWorkflow.cpp.
- A generic parameter is stored and displayed automatically, but using it in a
  new drivetrain, sensor, or control algorithm requires that algorithm to read
  or bind the value.
- Parameter values are currently temporary and return to JSON defaults after a
  Teensy reset. Persistent EEPROM/configuration storage has not been added.

6. BLUETOOTH DEBUG WORKFLOW LIBRARY
===============================================================================

Files:

    PlatformIO/lib/BluetoothDebugWorkflow/BluetoothDebugWorkflow.h
    PlatformIO/lib/BluetoothDebugWorkflow/BluetoothDebugWorkflow.cpp

Responsibilities:

- Start the Bluetooth UART.
- Start the Herkulex UART.
- place Herkulex servos in safe torque-off state at startup.
- Parse the embedded GUI configuration.
- Process incoming desktop messages.
- Advertise parameter and command definitions.
- Apply and confirm parameter changes.
- Route configured commands to built-in actions.
- Enforce Debug Mode for protected commands.
- Send state, logs, errors, and periodic telemetry.
- Pace definition messages to avoid overflowing the CH9143 radio link.
- Suppress duplicate startup definition bursts.

Incoming computer-to-robot message types handled:

- hello.
- request_definitions.
- command.
- parameter.
- parameter_request.

Outgoing robot-to-computer message types produced:

- telemetry.
- parameter_definition.
- parameter_value.
- command_definition.
- log.
- state.
- error.

Startup behavior:

1. Bluetooth Serial1 opens at 115200.
2. Herkulex Serial2 opens at 115200.
3. Broadcast torque-off is sent to servo ID 0xFE.
4. Embedded JSON is parsed.
5. The configured telemetry interval is loaded.
6. A ready log and safe state are transmitted.

Connection behavior:

1. Desktop sends hello.
2. Firmware sends a connected log and current state.
3. Firmware immediately sends definitions.
4. Desktop also sends request_definitions.
5. Firmware suppresses that request if definitions were sent within the last
   500 ms, avoiding duplicate traffic during radio startup.

The immediate advertisement was added because physical testing showed that the
matched bridge could occasionally deliver hello but lose the next back-to-back
request. Definition packets are separated by 40 ms, and normal telemetry is
limited to 5 Hz by default. This eliminated observed packet corruption without
requiring RTS/CTS wiring.

Current telemetry signals:

- system.uptime_s.
- system.debug_mode.
- system.stopped.
- bluetooth.messages_received.
- servo.last_id.
- servo.commanded_angle_deg.
- servo.measured_angle_deg, after the first successful angle read.
- servo.zeroed.
- servo.zero_offset_deg, after the selected servo has been zeroed.
- servo.auto_read_enabled.
- servo.responding.
- servo.tracking_fault.
- servo.position_error_deg, once a target and measurement are available.

Commanded angle records the most recent movement request. Measured angle records
position feedback returned by the servo and remains absent until a read succeeds.
Once zeroed, both commanded and measured angles are relative to the stored zero.
Absolute targets are checked against the servo's +/-160 degree protocol range.
Automatic monitoring tolerates individual packet losses. Three consecutive
read failures mark the servo unresponsive and set fault state. After a movement
has had its requested duration plus 300 ms to settle, three consecutive readings
more than 8 degrees from target set a tracking fault. Recovery clears the fault.

7. LOW-LEVEL ROBOT DEBUG SERIAL LIBRARY
===============================================================================

Files:

    PlatformIO/lib/RobotDebug/RobotDebug.h
    PlatformIO/lib/RobotDebug/RobotDebug.cpp

Responsibilities:

- Maintain a fixed receive buffer for serial bytes.
- Reassemble messages that arrive over several UART reads.
- Use newline as the packet boundary.
- Ignore carriage returns.
- Reject lines exceeding 767 bytes.
- Parse JSON with ArduinoJson.
- Reject malformed JSON and non-object JSON values.
- Call the workflow's message handler with an instance context pointer.
- Serialize outgoing JSON followed by a newline.
- Provide helpers for logs, errors, state, and parameter confirmations.

The callback was refactored to carry a context pointer. This allows the reusable
BluetoothDebugWorkflow instance to receive parsed messages without putting
application routing in main.cpp or relying on a global singleton.

9. SENSOR LIBRARIES
===============================================================================

IR library:

    PlatformIO/lib/Ir/Ir.h
    PlatformIO/lib/Ir/Ir.cpp

The project includes an IR abstraction. The configuration notes record that
analogue distance readings were too noisy for dependable ranging, especially
off-angle. The intended use is therefore object-presence detection with a raw
ADC threshold. The current configured threshold is 400 and requires tuning on
the installed sensors.

TOF library:

    PlatformIO/lib/Tof/Tof.h
    PlatformIO/lib/Tof/Tof.cpp

The project includes support structure for Pololu VL53L0X short-range and
VL53L1X long-range sensors, with shutdown lines intended to be controlled by an
SX1509 I/O expander. Address allocation and sensor counts are configured in
config.h. Final physical sensor count, bus layout, expander pins, and mounting
still require confirmation.

Neither sensor library is currently integrated into the minimal main program or
the active Bluetooth telemetry set.

14. SAFETY MODEL
===============================================================================

The desktop STOP button is a debugging convenience, not a physical emergency
stop. Wireless data can be delayed, dropped, corrupted, or disconnected.

Current firmware protections:

- Herkulex torque is disabled during workflow startup.
- Leaving Debug Mode disables broadcast servo torque.
- STOP disables broadcast servo torque.
- Herkulex movement requires Debug Mode.
- Servo ID, angle, and movement time are range checked in firmware.
- Parameter values are checked and clamped in firmware.
- Unknown message types, parameters, commands, and action names return errors.
- Oversized or malformed JSON messages are rejected.

Still required at robot level:

- Physical emergency stop or power cutoff.
- Safe actuator power-up procedure.
- Motor-driver enable handling.
- Hardware current limiting.
- Mechanical travel-limit verification.
- Communication-loss timeout for any future continuous motion commands.
- Watchdog strategy.
- Final validation of all placeholder limits.

Always perform first actuator tests with mechanisms clear and the robot lifted
or otherwise restrained. Start with small angle changes and keep a physical
power cutoff within reach.

18. HERKULEX DRS-0101 CONTINUOUS-VELOCITY CONTROL
===============================================================================

Continuous-turn support has now been added to the reusable Herkulex and
Bluetooth debug libraries. The DRS-0101 does not treat infinite rotation as a
position beyond its approximately 320-degree position-control range. It uses a
separate turn/velocity mode. The firmware therefore keeps position commands and
continuous-velocity commands as distinct operations.

The HerkulexTeensy library now exposes moveVelocity(). Its signed speed input is
limited to -1023 through +1023. The magnitude selects the requested drive level;
the sign selects direction. A speed of zero requests no rotation. The outgoing
S_JOG packet sets the DRS turn-mode bit and encodes negative direction with the
protocol's direction flag.

Two JSON-defined GUI commands were added:

- Set continuous velocity: accepts servo ID and signed speed.
- Stop continuous rotation: accepts servo ID, sends zero speed, and removes
  torque.

Set continuous velocity requires Debug Mode and the Run Robot state. The
suggested first test is a low magnitude such as +100 or -100 with the mechanism
clear. The firmware changes modes using the safe sequence required by the servo:
torque off, clear errors, send a zero-speed turn-mode command, torque on, then
send the requested velocity. The position command follows the corresponding
torque-off mode-switch sequence before executing a position move.

The ordinary STOP command also cancels the stored continuous-rotation state and
removes servo torque. While continuous rotation is active, position tracking
fault checks are suspended because a continuously turning shaft does not have a
fixed target. Automatic angle reads may continue, and telemetry now includes:

- servo.continuous_velocity_active
- servo.commanded_velocity

Zero Here is rejected while the selected servo is actively in continuous mode.
Stop Continuous Rotation first, then read/zero or issue position commands.

Recommended continuous-turn test sequence:

1. Ensure the mechanism can rotate freely.
2. Connect the desktop GUI to the CH9143 Bluetooth serial port at 115200 baud.
3. Enter Debug Mode.
4. Press Run Robot.
5. Use Set continuous velocity with speed +100 or -100.
6. Confirm the direction and telemetry.
7. Press Stop continuous rotation before changing operating modes.

-100 through +100. begin() attaches both pulse outputs and immediately commands
neutral, so startup does not deliberately turn either motor.

The JSON catalogue now creates Set 203 DC motor speed and Stop 203 DC motor
controls. Motion requires Debug Mode and Run Robot. The dedicated motor stop,
global STOP, and leaving Debug Mode all write the 1500-microsecond neutral pulse.

- dc_motor_203.active
- dc_motor_203.channel_a_percent
- dc_motor_203.channel_b_percent
- dc_motor_203.channel_a_pulse_us
- dc_motor_203.channel_b_pulse_us

The firmware compiled and uploaded successfully to the Teensy through COM7 on

- Channel A uses TX3/pin 14.

- Two Servo objects are attached with plain attach(pin), matching the example.
- The speed control now accepts channel_a_percent and channel_b_percent.

The 8x8 TOF page gained a Raw/Fused view selector. Raw displays the exact 64
sensor measurements. Fused retains the same 8x8 dimensions but combines each
zone with agreeing cardinal neighbours and its previous-frame value using
weighted averaging. Depth-difference gates prevent blending across likely
object boundaries, and invalid measurements are not introduced into valid
zones. Switching the selector immediately redraws the latest received frame.
The updated desktop source passed Python bytecode compilation and repository
whitespace validation.

The earlier fused-grid interpretation was replaced after clarification. The
view selector now offers Raw grid and Smoothed image. Raw grid retains all 64
numeric cells. Smoothed image converts the same 8x8 distance colours into an
enlarged bilinearly interpolated heatmap, producing the continuous blurry-image
appearance of a low-resolution thermal camera without claiming extra measured
spatial resolution.

A third 8x8 view, Stable detail, was added for dependable interpretation. It
maintains five raw frames and filters every physical zone independently using a
temporal median followed by conservative smoothing. Invalid samples can be
covered briefly by recent valid measurements, while changes more than 250 mm
nearer are accepted immediately so a newly appearing obstacle is not hidden by
old history. Farther jumps remain filtered so a single noisy reading cannot
make an obstacle disappear. No neighbouring zones are averaged, preserving measured boundaries.
The filtered map is displayed with the same smooth colour interpolation.

The recording Weight8x8.rdbg was analysed directly for matrix performance. It
contained 263 valid 8x8 frames across 65.20 seconds, averaging 4.02 Hz. The
median frame interval was 0.249 seconds and the longest was 0.319 seconds. A
typical frame contained all 64 valid zones and the minimum was 63. Consecutive
valid measurements had a median absolute change of 0 mm and a 95th percentile
of 72 mm; 2.86 percent changed by more than 250 mm. The scene changed strongly
throughout the test, including an object approaching from roughly 304 mm to
74-91 mm before the final view became broadly uniform near 300-370 mm. The
recording showed healthy acquisition and transport, with the main caution being
occasional large edge/range transitions that benefit from obstacle-safe
temporal filtering.

The 8x8 view selector gained Raw v2. It presents a smoothly enlarged current
frame, colours measurements below 200 mm neutral grey, and removes isolated
spatial spikes. A pixel is replaced by its neighbourhood median only when at
least four valid surrounding pixels agree within 250 mm and the candidate
differs from that median by more than 600 mm. This deliberately retains coherent
near objects, wide changes, and genuine depth edges rather than applying a
blanket blur.

The recording WeightWallTubeWall.rdbg was analysed for the angled black-wall
case. It contained 177 valid matrix frames over 43.79 seconds at 4.02 Hz, with
63-64 valid zones per frame. Normal consecutive changes were small (median 2 mm
and 95th percentile 43 mm), but the dark angled surface caused coherent groups
of upper zones to jump from the approximately 500 mm wall surface to roughly
1500-1900 mm, with occasional transitions above 3000 mm. This is a low-return
or grazing-angle depth failure affecting adjacent zones, not isolated random
noise. The isolated-pixel Raw v2 filter therefore cannot safely remove all of
it; a future surface-consistency/persistence stage is required.

The 8x8 selector gained Dark surface safe. This mode accepts nearer changes
immediately but requires a jump more than 400 mm farther to persist for three
frames before discarding a known nearer surface. It then performs two
conservative surface-repair passes: a far zone is replaced only when at least
three surrounding zones agree within 220 mm and the zone is more than 450 mm
behind their median. The limited passes can repair small coherent dark-surface
holes without flattening large genuine openings. Values below 200 mm use the
same neutral-grey display treatment as Raw v2.
